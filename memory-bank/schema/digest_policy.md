# Digest Policy

## 文档目的
本文件定义什么是 digest、什么时候应该 digest、digest 后页面应达到什么可用程度，以及哪些行为不属于 digest。

## digest 管什么
1. 将原始源码、文档或资料切片后做局部语义消化。
2. 为页面补充“可操作”的语义信息，例如：
   - 模块职责
   - 关键符号
   - 执行流程
   - 外部依赖
   - 风险点
   - 修改入口
3. 为 review / modify / debug 提供可直接引用的局部熟知识。

## digest 不管什么
1. 不直接修改 Raw Sources。
2. 不直接执行 patch。
3. 不替代验证、回归测试或 reconcile。
4. 不等于全文总结全项目。
5. 不在本步定义全部自动化调度细节。

## 何时必须 digest
1. 目标页面仅为 `raw_ast` 时。
2. 当前任务涉及的 symbol 缺少可操作语义摘要时。
3. 小模型如果不 digest 就必须整文件硬读时。
4. 调试时只能看到错误点、看不到上下文职责时。

## 何时应优先局部 digest
1. 单函数或单文件修改任务。
2. Review 只聚焦少量 symbol 时。
3. Debug 已有 traceback 且出错范围较小。

## digest 输出要求（初版）
至少应补充：
- 角色 / 作用
- 关键 symbols
- 主要流程
- 依赖关系
- 边界条件
- 风险点
- 推荐修改入口
- 来源追踪

## 页面状态转换原则（增强版）
### 本步已拍板
允许页面状态由三类事件触发转换：
1. **时间触发**：页面在超过一定时效窗口后，可被标记为需要复查。
2. **Git / 文件变化触发**：当源文件变化时，相关页面可转为 `stale` 或待 reconcile。
3. **人工命令触发**：如 `/digest`、`/reconcile`、人工归档或人工替换。

### 当前只固化到“触发类别”
本步只定义“哪些类型的事件可以触发状态变化”，暂不锁死：
- 具体几天后自动转为 `stale`
- 自动任务多久跑一次
- 哪些变化必须直接转 `stale`，哪些只进队列
- 历史页与 superseded 页的精确自动判定算法

## digest 状态转换（初版）
- `raw_ast` -> `partially_digested`：仅补充了部分可操作语义。
- `partially_digested` -> `digested`：足以支持目标任务，不必再整文件通读。
- `digested` -> `stale`：源材料变化、时间过期或人工判定需复查。
- `stale` -> `digested`：完成补 digest / reconcile，并再次满足当前任务可用标准。
- `historical` 与 `superseded` 的精确进入条件延后到冲突与归档步骤细化。

## digest 规模控制
1. 优先按 symbol、span、anchor 做局部 digest。
2. 只在必要时扩大到整个文件。
3. 避免一次 digest 过多文件，防止 32K 上下文浪费。

## 验收口径
一个页面可被认为“对当前任务足够 digest”，前提是：
1. 它能解释模块/符号做什么。
2. 它能指出改动入口或审阅重点。
3. 它能提醒主要风险和依赖。
4. 小模型不需要再全文阅读才能继续下一步。
